## 三、可靠性：上游 schema 不一致（本次新发现）

run2 P2 第 17 次起连续返回：

```
embed-http-400: {"error":{"message":"Invalid JSON payload received. Unknown name \"requests\": Cannot find field. (reque...
```

这是 **Gemini 原生 schema** 的报错——中转把 OpenAI 形态的请求打到了**另一种 API 形态的上游后端**。特征：

- **成簇出现**（run2 里一次簇 ≈ 30 次失败），不是均匀分布；可靠性专项 5 分钟内只遇到 1 次（首个请求）→ 间歇性路由问题。
- **代理与直连都遇到**（P8 直连第 3 次同错）→ 与代理无关，是上游。
- **跳闸按设计生效**：3 连败 → 退避 10s → 再败 → 20s（`embed-circuit-open`），窗口内调用立即失败而不是继续占着 `dbGate` 等超时。
- 注入路径不重试 → 直接 skip；写路径 15s+重试 1 次仍可能连败 → 拒写。

## 四、判据与建议

1. **注入 3s 硬顶对当前端点偏紧**：实测超 3s 概率 **13.5%（合计）/ 最高 23%（单窗口）**。三条路：抬到 4~5s（代价：闸持有更久、劣化日堆积）、维持"超时即跳过"（现状，设计正确但用户感知是"记忆时好时坏"）、或降载（注入形态已是合批后的最小形态，无空间）。
2. **需要劣化判据（目前没有）**：建议 **单文本 p50 > 2s 判劣化**（本晚已越过），并把它接到哨兵（`dsh-sentinel.sh`）——比事后看 skip 率更早。
3. **批 32 → 建议降到 8~16**：批 32 的 max 19.5s 会撞穿 15s 写预算；并发 5×批 8 的实测总耗时 ~3s，更划算。
4. **400 簇要单独计数**：`embed-http-400.*"requests"` 应进哨兵（与 `artifact-rebuild-failed` 并列），并向中转方反馈——它比延时更能解释"整段时间注入全 skip"。
5. 直连可用（不强制代理，本晚 p50 与代理相当），但仍会遇到同一个 400。
