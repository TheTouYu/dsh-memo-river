## 四、续修：无头记录日志（部署后发现，已闭环）

全库复扫发现 **8 个桶的 `emb-cache.bin` 是「无头记录日志」**：记录全合法（keyLen/vecLen/边界都对），
只缺开头 16B 的 `MREC` 头（例：`3f000000 000c0000` = keyLen 63 / vecLen 3072）。

**成因（定位到具体窗口）**：`fs.promises.writeFile(path, header, {flag:'wx'})` 是「先 `O_CREAT|O_EXCL`
把文件建成 0 字节、再写数据」——在这个窗口里，若同路径的另一实例或**进程 exit 兜底**（`flushSync`）
走到 `EEXIST` 分支，旧代码把 `EEXIST` 当「头已就绪」，于是 `appendFileSync` 把记录追加到了无头文件上。
典型触发场景：短命进程（验收子会话 / 探针）在落盘进行中被 teardown。

**修法两条腿**：
1. **堵写方**：`ensureHeader`/`ensureHeaderSync` 遇 `EEXIST` 一律**验头**（读 4 字节比 `MREC`）；无头时先
   `mergeExistingSync()` 把磁盘已有记录并回内存，再连头全量重写（tmp+rename），并**跳过本次 append**
   （重写已含本批 pending，再 append 只会多一条死记录）。
2. **救存量 + 留取证**：`scanBin` 认出无头记录流 → 条目照收、载入时补头写回，并打一行取证日志
   （「写方把记录追加到了无头文件上」）——下次再出现就能顺日志抓到写方。8 个桶已就地补头，
   复扫 188 份 `.bin` 全部有头（22.16MB）。

**验证**：`scripts/probe-emb-cache.mjs` 扩到 **36/36**，新增 [G] 无头自愈（条目全收/魔数修好/可继续追加）
与 [H] EEXIST-但无头两种窗口（有记录 & 0 字节）：两边条目都在、落盘后有头。
