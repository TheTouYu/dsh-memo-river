## 一、病根（一句话）

`EmbedClient` 构造时整读 `emb-cache.json`、任何新增嵌入后 `writeJsonSafe` **全量同步重写**：
genshin 桶 116MB/1764 条（活 chunk 仅 184）单周期 read+parse+stringify = **573MB 峰值、1.16s
同步 CPU**；`writeFileSync` 冻结事件循环 → WS 心跳超时 → 在飞回合被打断；跨桶并行叠加 →
12:42 KILL 3G / 13:40 ABRT 2.5G / 14:25 ABRT 2.6G。

## 四、续修：无头记录日志（部署后发现，已闭环）

全库复扫发现 **8 个桶的 `emb-cache.bin` 是「无头记录日志」**：记录全合法（keyLen/vecLen/边界都对），
只缺开头 16B 的 `MREC` 头（例：`3f000000 000c0000` = keyLen 63 / vecLen 3072）。

**成因（定位到具体窗口）**：`fs.promises.writeFile(path, header, {flag:'wx'})` 是「先 `O_CREAT|O_EXCL`
把文件建成 0 字节、再写数据」——在这个窗口里，若同路径的另一实例或**进程 exit 兜底**（`flushSync`）
走到 `EEXIST` 分支，旧代码把 `EEXIST` 当「头已就绪」，于是 `appendFileSync` 把记录追加到了无头文件上。
典型触发场景：短命进程（验收子会话 / 探针）在落盘进行中被 teardown。

**修法两条腿**：
1. **堵写方**：`ensureHeader`/`ensureHeaderSync` 遇 `EEXIST` 一律**验头**（读 4 字节比 `MREC`）；无头时先
   `mergeExistingSync()` 把磁盘已有记录并回内存，再连头全量重写（tmp+rename），并**跳过本次 append**
   （重写已含本批 pending，再 append 只会多一条死记录）。
2. **救存量 + 留取证**：`scanBin` 认出无头记录流 → 条目照收、载入时补头写回，并打一行取证日志
   （「写方把记录追加到了无头文件上」）——下次再出现就能顺日志抓到写方。8 个桶已就地补头，
   复扫 188 份 `.bin` 全部有头（22.16MB）。

**验证**：`scripts/probe-emb-cache.mjs` 扩到 **36/36**，新增 [G] 无头自愈（条目全收/魔数修好/可继续追加）
与 [H] EEXIST-但无头两种窗口（有记录 & 0 字节）：两边条目都在、落盘后有头。

## 六、GLM 独立核验的口径对账（2026-10-14 晚）

| 项 | 原报告 | 独立复测 | 处置 |
|---|---|---|---|
| 探针 F 段阈值 | `bin<15MB` | 该阈值按 **1024 维**假设写的，genshin 实为 3072 维 → 未清淤全量 24.9MB **必红** | GLM 已修（`e4dc9d0`：夹具回退 `.precompact-*`、阈值改 <30MB），探针 36/36 |
| 「膨胀 16 倍」 | 引用任务书的 16× | 源自 1024 维误估；3072 维真值 = 未清淤 **24.9MB ≈ 4.6×**，清淤后 3.3MB 是常态 | **以 4.6× 为准**，16× 作废 |
| 遗留 JSON 计数 | 「2 份 12.7MB」 | GLM 见「1 份 9.9MB」 | 两者非同一口径：实际 **2 份 = 10.28MB + 2.46MB = 12.74MB（十进制）**；GLM 的 9.9MB 是最大那份的 **MiB** 读数（9.80 MiB），小那份被漏计 |
| 闸门退出码 | 「复跑 37/37」 | 管道里 `tail` 会吃掉退出码 | 采纳：**闸门必须拿真 EXIT**（后续一律 `echo $?` 落 status 文件） |

**结论：第三路径已定位并修复**（判据：修复版 acceptance 复跑后无头集合零新增）。

第三路径的形态（acceptance 复跑实锤，非推测）：**头是 `headerEnsured` 在内存里的记忆，不是盘上的事实**——
测试拆桶 `rmSync(bucketRoot)` / 外部清理把 `.bin` 删掉后，实例仍以为头在，下一次追加就把路径**重新建成无头记录日志**。
判据链：①修复版 acceptance（真 EXIT=0，37/37）跑完仍新增 3 个无头文件（17:18:46/17:19:01，24.8/26.0/50.0KB）；②这三个桶只有 `.bin`+日志、无库无 dailynote，且全库**没有任何 `.corrupt-*` 留证**（排除「改名留证」路径）；③解出的键还是验收夹具。

**修法（第三版）**：把「验头」从「头一次」改成「**每次 append 前都验**」——
- 新增 `appendGuardedSync()` / `appendGuarded()`：append 前读盘上头（`'ok' | 'nofile' | 'short' | 'noheader'`）；非 `ok` 就 `mergeExistingSync()` + 连头全量重写（`rewriteWithHeader`），**绝不 append**；`nofile && fileBytes===0` 才是「真·新桶」→ 建头 + 追加。
- `load()` 对 **0 字节/短于头**的文件不再改名留证（那是另一实例正在 create 或刚被清掉的中间态，改名会把别人正在写的文件挪走）——只有「有内容但头/版本/维度不对」才 `.corrupt-<ts>`。
- 删掉已被 `appendGuarded*` 取代的 `ensureHeader`/`ensureHeaderSync`（避免留一份看似是安全机制的死去代码）。

**验证**：探针 **28 → 36 → 43/43**，新增 [I] 文件被删/目录被删/0 字节中间态、[J] **子进程真 exit 的 flushSync 通道**（此前从未被测到——本轮 tsc 报 `statSync` 未导入，暴露出「type error 仍会 emit、探针跑的是陈旧 emit」这个假绿陷阱，J 段就是为堵它加的）。

## 八、套件卫生整改（`aa5bb13`，2026-10-14 晚）

起因是本案追查被「假桶」误导（详见 `docs/BUG-1014-headless-bin-third-race.md` 结案节）：套件把 cwd 放
tmpdir 却**不设 `DSH_HOME`**，数据桶于是落在**生产柜子**里，每跑一次留 7~14 个永久空壳。普查：
**288 桶里 186 个空壳**，其中 **35 个是最近 2 小时 5 次验收跑出来的**（之前 22 小时只多 1 个）；
字节只有 1.15MB——危害是语义污染 + 取证现场被污染。

**模型修正（本次教训）**：隔离不能一刀切。先按「给 12 个套件都接线」实施，结果 **8 个套件隔离后立刻
EXIT=2**——它们依赖 `setup-selftest.mjs` 预铺的 `.selftest/教室建模{归档,孤岛,写入测试}` 三个夹具，
隔离出空 DSH_HOME 后环境自检必红。最终：

| 类别 | 处置 |
|---|---|
| 4 个不依赖预铺夹具（adaptivek / patrol / selection-weights / write-prompts） | 接 `scripts/isolated-env.mjs` 自建自净；各自隔离版实测 **真 EXIT=0** |
| 8 个依赖预铺夹具（acceptance.mjs / -consolidation / -merge / -p3 / -tiebreaker / -title-gate / -update / -usage） | **不隔离**（`acceptance.mjs` 已按字节恢复原样），改用 `scripts/clean-junk-buckets.mjs` 定期清扫 |
| 运维件 import-dailynote / reimport-orphans | **故意**不隔离（它们就是对真桶干活的） |

**两个坑**：①`scripts/lib/` 会被 `.gitignore` 的 `lib/`（构建产物）一起忽略 → helper 落在
`scripts/isolated-env.mjs`；②**`setup-selftest.mjs` 缺省用本地 hash 嵌入桩**（`REAL_EMBED=1` 才走真端点），

**闸门复跑序列**：run8 25/37（桩向量）→ 真向量重建 → run9 34/37 → run10 **36/37**（仅 #8 红；#8 是
