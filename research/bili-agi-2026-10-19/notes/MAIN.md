## 一、结论先行：这 28 个视频对本仓最有价值的 5 个点

### 1. 「主动压缩」压倒「满了再压缩」——本仓压缩 nudge 的设计有根本性缺陷

来源：**BV1qAMR6MEA4**（裘香莲，主动上下文压缩 opencode-acp / billion-context-pi，1820s）

这条与本仓 `billion-context-dsh` 插件同源，视频里给出的实测数字值得逐条对照：

| 维度 | 传统压缩（满了再压） | ACP（主动压缩） |
|---|---|---|
| 触发时机 | 80–90% 才被动触发（实测 90 万 token 才动手） | 持续压缩，增长 5 万 token 阈值就建议压 |
| 缓存 | 压一次**前缀全废**，下次请求零缓存 | 前缀几乎不动，缓存命中率 98–99% |
| 上下文常驻量 | 50 万–70 万 token | 10 万以下（均值 11 万，峰值 25 万） |
| 原始信息 | 压错了**找不回来** | 原始消息不动，可 `decompress` 无损重建 |
| 可搜索 | 无 | `search_context` 定位 → `decompress` 取原文，**三步内恢复** |
| 压缩粒度 | 整段压成一个大总结 | 一块一块压，**每压一次产生一个几十比一的块** |

视频里的核心洞察（对我们直接可用）：

> **压缩不是删除，是折叠。原始信息保留在原始 session 文件里，用 decompress 可以无损重建。**

这正是我们 `search_context` + `decompress` 的设计意图。但**触发时机**我们做错了——我们的 nudge 是在上下文快满时才触发（看到 `+49.6K since last nudge` 这类提示），而 ACP 的判据是「增长 5 万 token 就压」。

**可直接用**：把压缩 nudge 的触发判据从「占比阈值」改为「增量阈值」（每涨 ~50K token 就压一次），并保证压缩块小（几十比一），不要攒到最后压成一个大总结。

视频里还有一个诚实的质量自评，我们可以照搬其测试方法：

> 压缩后「凭记忆陈述技术细节 → 从代码库 gate 中直接对比」，67 个压缩块**全部精准命中**，连行号都对。
> 但**论证推理过程的逐字记录会更早被折叠掉**——「技术代码保真，论证推理过程不是」。

这解释了为什么我们的 `structural_explanation` 类日记在多次压缩后容易丢论证链：**压缩保事实不保推理**。→ 反过来，**推理链类的知识应该在写入时就把论证结构显式写进正文**（我们的「结论先行 + 因果链」写法正是对此的正确防御）。

### 2. 记忆系统的评估框架三问——可直接拿来审计我们的语料

来源：**BV14seb6EEVP**（为什么叫QQ，Supermemory，698s）

> 评估任何记忆系统的三个问题：
> 1. **它会不会更新事实？** 是会过期的系统知不知道新事实推翻旧事实
> 2. **它会不会遗忘？** 没有衰减机制的记忆库三个月后就变成垃圾场
> 3. **它给不给得动？** 是每次都等你去搜，还是提前把画像准备好、在会话开始那一刻就交出去

对照本仓：

| 三问 | 本仓现状 | 判据 |
|---|---|---|
| 更新事实 | ✅ 有 `memo_supersede`（G3 取代/废止） | `memo_supersessions` 表 |
| 遗忘 | ⚠️ **弱**。只有「未被召回」这一被动衰减，没有主动作废机制 | 未覆盖率 0.4%，但「从不被召回」的篇目没有强制清理 |
| 主动供给 | ❌ **缺**。我们只有被动召回（每轮 KNN），没有「用户画像」这一层 | 无 user profile 概念 |

**第 3 点是最大缺口**：Supermemory 的「用户画像」是两层——静态层存长期稳定事实，动态层存最近状态，**每次会话开始一次调用 50ms，画像直接注入系统提示词**，模型连搜都不用搜。我们的被动召回是每轮重新做 KNN，没有这个「画像」缓存层。

**需改造**：这个思路可以映射到我们的「工作区桶」上——每个桶应该有一份自动维护的 `画像.md`（项目是什么、当前在做什么、关键决策），会话开始时注入，而不是每轮靠 KNN 现捞。

来源里的关键数字：95% 召回只多花 **720 个 token**（上下文占用压缩 99.4%）；LongMemEval/LoCoMo/ConvoMem 三个基准第一。

**但视频自己也泼了冷水，这条必须记住**：

> 所有厂商的基准分数都是自爆的。Supermemory 说自己 95%，Mem0 说 93.4%，同一个 LongMemEval 换三个答题模型跑出 **85.2 / 84.6 / 81.6** 三个分数。**分数跟着配置走，不跟着品牌走。**

### 3. 上下文信息密度最大化：30K token 预算 + L0/L1 常驻 + L2-L4 按需

来源：**BV1Z7RNBmENU**（老汤的碳基突围，GenericAgent，329s）

复旦梁家青团队的 GenericAgent：3300 行种子代码、92 行主循环、**9 个工具**，在 Lifelong Agent Bench 上跑出 100% 完成率，token 消耗是 Claude Code 的 14%、OpenClaw 的 16%。

三种上下文失败模式（我们的 600 token 注入预算正面临同样问题）：

1. **位置偏差**——重要信息埋在中间，模型看不到
2. **噪音污染**——无关内容不是零贡献，是**负贡献**
3. **有效窗口缩水**——你以为有 200K，实际有效可能就 20K

他们的解法是**上下文信息密度最大化**三约束：完整性（决策关键信息在）、简洁性（其他排除）、自然性（模型易懂）。

**五层分层记忆（最精妙的部分）**：
- **L0** 行为准则 — 常驻
- **L1** 索引层 — **只存「我会点外卖」这种标记，不存完整流程** — 常驻
- **L2–L4** 全部按需检索

结果：积累 20 个技能后，OpenClaw 提示词膨胀到 43000 token、Claude Code 22000、**GenericAgent 只有 2298**——因为 L1 只记一行索引，真需要了才从 L3 把完整 SOP 拉出来。

**可直接用**：我们的日记正文就是「完整 SOP」，每轮召回就整篇塞进去。**应该拆成两层**：
- 索引层（常驻/高权重）：标题 + Tag + 一句话结论
- 正文层（按需）：完整论证，只在 L1 命中后展开

我们的 `memo_recall` 默认 120 字截断其实已经在做「索引层」，但**被动注入**仍然塞正文片段。这是一个可测量的优化点。

**自进化铁律**：`No execution, No memory`——没跑通就不记。九轮重复 GitHub 研究任务 token 从 22 万降到 2.3 万（**-89.6%**），LLM 调用 32→5 次，时间 7 分半→1 分 38 秒。

> 论文原话：**更少的 token 往往对应更好的表现**。压缩后的精简记忆反而比完整记忆成功率更高 **66.48% vs 52.44%**。

**需改造**：我们的 `writeNudge` 节律提醒没有「验证过才写」的约束——建议加一条：写日记前先确认这件事有验证读数（命令退出码、测试结果、行为观测），没有就不写。

### 4. VCP 上游的「上下文语义引力场」：按语义分段 + 曲率阈值决定展开

来源：**BV1SZ5U6ZEsN**（VCP 上下文引力场，作者 lioensky 团队的衍生讲解）

我们的记忆算法上游 VCPToolBox 的核心机制，这条视频把它讲得比源码清楚：

- **不是逐句分块，是按语义分段**——「这一段讲什么内容」通过内容的语义差分切成段，而不是「A 一句 B 一句」
- 每段在向量空间是一个 3072 维归一化坐标
- 段与段之间算「语义引力」的方向与**曲率**
- **判据是欧式距离阈值 0.3**：距离 ≤0.3 → 对 AI 显示这一段；>0.3 → 关系不大，不显示
- 0.5 附近引入 description 做精细化判断

用途：
1. **上下文折叠 V2**：话题转向代码时，把开头的问候段、聊番剧的段落「收纳折叠成一句话」
2. **工具选择预判**：算上下文与各工具的语义距离，决定 AI 该知道哪些工具
3. **跨 AI 传递多模态**：图片的 base64 通过语义引力场「弹」给另一个 AI，不用文字转述

> ⚠️ **重要换算警告（先前的误判已被推翻）**：视频明说用**欧式距离**、向量**已归一化**。
> 归一化单位向量上 `d² = 2 − 2cos`，所以：
> - 欧式 d=0.3 → **cos 0.9550**；d=0.5 → **cos 0.8750**
> - 本仓 gateThreshold=0.55 → 欧式 d=0.9487；minKnnForReward=0.6 → 欧式 d=0.8944
>
> **两者差一个量级，不是同一把尺子。** 把 0.3 当余弦阈值用 → 门控彻底放空；
> 把 0.3 当余弦相似度用 → 什么都不显示。**「用 VCP 的 0.3/0.5 校准本仓 Ω 阈值」这个想法在算术上不成立，已从改进项中划掉。**
>
> 另有一条不确定：视频同时提到「测地线查询」，若真是测地距离则上述换算不成立——已在
> `notes/memory-systems.md` §二 标为假设，未臆断。

**真正可迁移的是「三档 + 中间档二次判断」的决策结构**，不是它的数值：本仓 `thematic_neighbor`
（Ω 低时由 structural 降级）就是「中间档」产物，但**没有「中间档再做一次精细判断」这一步**。
实验方向：在 `gateThreshold` 附近的窄带（如 0.50–0.60）用「标题 + Tag」再算一次相似度做二次判断。
**判据**：`src/config.ts:gateOnCurrentMessage` 注释里的三条负例（天气/晚饭/订票，w1 得分
0.4536/0.4830/0.5124）在改动后仍被拦下。

### 5. Δ 一个反直觉的发现：压缩保代码不保论证

这句值得单独强调，因为它是**从实测中发现的、不是设计出来的**：

> 「技术代码保真，但论证推理过程的逐字记录会更早进块——即那些推理过程都给忘掉。」

BV1qAMR6MEA4 的原话。

对我们意味着：**如果你的知识库承载的是「为什么这样做」而不是「做了什么」，压缩会系统性摧毁它**。而我们的日记恰恰写的是决策与因果链（Tag: 归因纠偏 ×47、证据分级 ×58）。

**行动**：在压缩摘要里**显式保留决策的 because 从句**——这正是我们压缩工具描述里已经写的「决策和理由」，但从实测看，这条规则在实际压缩时容易被抛弃。→ 需要一个**压缩后自检**：随机抽一个压缩块，问「这条决策的理由还在吗」。

### 6. 强交叉验证：向量召回 + 图联想的两段式，是同类系统的共同架构

来源：**BV1s8411Q7oa**（东风篱影，AI 派蒙桌宠长期记忆，900s）

这条是本轮**最有价值的交叉验证**，因为它与我门的架构独立同源：

> 派蒙的实现：
> 1. 用户说话 → whisper 转文字
> 2. **embedding API 把话转成向量 → 在向量数据库（RAMA/Chroma 类）里找语义最接近的历史记忆**
> 3. **再用图数据库做「联想性回忆」——找到与这条记忆相邻的节点或次相邻的节点**
> 4. 把「语义相关记忆 + 联想关联记忆 + 人设」一起打包给模型

作者对第 3 步的解释非常精确，正是我们 TagMemo 的设计理由：

> 「从向量数据库里匹配出来的记忆只是**语义上比较接近**的历史记忆，但真正的人类思维都是非常跳跃的，
> 很多时候我们回忆一件事情会把与这件事情**相关联**的其他记忆也回忆起来，而不仅仅是语义相似的记忆。」

**这就是我们 `TagMemo`（Tag 共现图扩展）的完整动机陈述。** 我们不是特例，这是记忆系统的标准两段式架构：

| 阶段 | 派蒙桌宠 | 本仓 |
|---|---|---|
| 语义召回 | OpenAI embedding + Chroma | bge-m3 + KNN |
| 联想扩展 | 图数据库邻居/次邻居 | TagMemo 共现图扩展 |
| 结果注入 | 打包给人设提示词 | 注入带 role 标签的片段 |

**结论**：我们的架构选择是对的，且已被独立实现验证。**但**注意派蒙作者的第 4 点——他把「人设」和「记忆」一起打包，也就是 **profile 与 recall 是同一层**。对照第 2 节的 Supermemory：**画像（profile）应该是一等公民，在注入时优先于搜索。** 这两条指向同一个结论。

**附带教训（作者明确说的）**：用**流式调用**做语音，输出一句就播一句，「响应速度提升不止一倍」。我们对延迟的优化方向（嵌入往返 40ms 已解决）与之同源。

### 7. 娜迦 3.0 的反面教材：每轮回忆会造成迟滞

来源：**BV1n6gNzoECH**（柏斯阔落，娜迦 3.0，343s）

> 3.0 beta 的逻辑是每一个对话都会回忆，这就会造成在日常对话中 AI 的回复会有迟滞，说白了就是反应慢。
> 人类在对话过程中不会这么做——你在餐厅里点菜，会因为服务员说一句「你要吃什么」就疯狂回忆以前听到过这句话吗？
> **人的回忆更多是一个你主动回忆的过程，而不是靠灌输给你这些内容。**

娜迦 3.0 的修法：给记忆系统加了 MCP 协议，**让 AI 能主动查询记忆**；日常运作靠代码设定（提示词）。

**这是对我们「每轮无条件被动注入」的直接质疑。** 对照我们的门控：目前有 gate（空查询抑制），但**没有「这个话题值不值得回忆」的判断**。

**需改造**（与 VCP 语义引力场的 0.3 阈值可以合并成一个改进）：被动注入前先做一个轻量的「相关性预判」，距离远的就不注入。这与视频 4 的曲率阈值判据一致。

## 二、次要发现（有启发性但不直接可迁移）

### 2.1 分层压缩的层级语义（BV1qAMR6MEA4）

作者做了 T1/T2/T3 三级压缩，并给出了**每级的记忆保真度衰减**：

| 层级 | 保留什么 | 类比 |
|---|---|---|
| T1 | 完全精确保留信息，可 decompress 无损重建 | 昨天的事 |
| T2 | 大致知道这件事，细节不记得了 | 一个月前的项目 |
| T3 | 只知道项目大概有什么、核心要点 | 很久以前的经历 |

**T1/T2/T3 能撑多久**：100 万上下文、按该压缩频率，**T3 要到 600 多亿 token 才触发 ≈ 8 个多月**；开 T4 可以持续几年。

本仓的压缩目前只有「一层」（压缩块 + decompress）。要不要引入 T2/T3 取决于：**我们的块会不会无限增长**。目前看会（压缩块本身不被再压缩，只累积）。→ 这是一个**结构性风险**，值得记一等。

### 2.5 工具面开关化省 token（BV1SzPJzwEnN，Proma 0.6.0）

> 「为了让降低大家对于整个 tokens 的消耗，所以我们把 MCP 和 skills 都做成了**开关**……
> 如果你不需要做 PPT、不需要做 PDF、不需要处理表格，那就把它关掉，这样会省不少的 tokens，同时速度也会比较快。」

**可直接用**：我们的记忆插件工具面（memo_recall/write/update/merge/supersede/patrol/stats/tags/drafts/approve/discard/tuning，12 个）一直是全量挂载。**按场景开关**（如「只读会话」关掉所有写工具、「巡检会话」只留 patrol/stats）能直接省工具描述 token。

同源的还有 eve 的 `needs_approval` 设计（BV1PCjx6oEeJ）：

> 在工具定义里加一行 `needs approval` 判断，比如发现 SQL 查询超过 50GB，agent 就会自动停下来等你点个头才继续。

**可直接用**：我们的破坏性工具（`memo_merge` 归档源篇、`memo_supersede` 标记失效、`memo_approve` 批量入库）都**没有前置审批**，靠调用方自觉。加一个 `needs_approval` 形态的闸门（如「merge 超过 N 篇需要确认」）是对齐本仓 AGENTS.md「破坏性闸门」条款的机制化落地。

### 2.6 eve 的另一条：文件系统即 Agent（BV1PCjx6oEeJ）

RSC 出的 `eve` 框架，核心是 **File system first**：
- 一个目录 = 一个 agent（`agent.ts` 配模型、`instructions.md` 是系统提示词）
- `tools/` 下建个 ts 文件，**文件名就是工具名**，构建时自动发现
- `skills/` 下丢个 markdown，模型需要时自动加载
- 底层集成 `workflow sdk`：**自带持久化执行，每步 checkpoint，崩溃后从已确认步骤继续**

「skills 目录丢 markdown，需要时自动加载」——**这正是我们记忆河流的 `dailynote/*.md` 形态**。我们的做法与主流框架的选择一致。

**需改造**：eve 的 checkpoint 语义（「已完成步骤不重跑」）我们没有——memo_write 失败重试会重复写入（虽然有去重闸门）。这是工程健壮性层面的差距。

## 三、方法论层面的元观察

### 3.1 这批视频的共同主线

28 个视频里，**至少 12 个在讲同一件事**：*上下文不是越大越好，是越干净越好*。

- 主动压缩（BV1qAMR6MEA4）：10 万 < 50 万
- 信息密度（BV1Z7RNBmENU）：30K 预算 > 200K 预算
- 语义引力场（BV1SZ5U6ZEsN）：按距离阈值折叠无关段落
- Supermemory（BV14seb6EEVP）：「记得多不如忘得干净」
- CLM（BV1gya667EV6）：FLOPs 大幅下降还反超 SOTA
- Headroom（BV1Xg7v6PEDK）：代码搜索省 92% token

**这是行业共识，不是个别观点。**

### 3.2 与我们已有结论的交叉验证

记忆河流里 D239《记忆片段选择的论文灵感地图——七族回答三个正交问题》提出「①该不该给 ②给多细 ③给了会怎样」。这批视频正好补上**②「给多细」**的工业实践答案：**分层（L0/L1 常驻 + L2-L4 按需）+ 索引层只存标记不存流程**。

D241《判别式决策》：双向编码器一次前向给候选项打分 26ms。与 Supermemory 的「画像 50ms 一次注入」是同一量级的设计取向——**把判断成本前置、把判断结果缓存**。

### 3.3 需要警惕的偏差

1. **样本偏差**：这 29 条来自用户收藏夹，是**用户已经筛选过的兴趣**，不代表 AGI 领域全貌。收藏时点的技术判断未必正确。
2. **幸存者偏差**：能上 B 站推荐/被收藏的项目，多是「有故事可讲」的。GenericAgent 8.4K star 但视频自己说「开源不到 4 个月，生产稳定性没验证过，benchmark 主要在编码和研究任务，金融任务只有 65%」。
3. **基准自爆问题**（BV14seb6EEVP 明确指出）：「所有厂商的基准分数都是自爆的」。要把这些数字**当宣传材料看，不当验收标准**。唯一可信的判据是**在自己的真实数据上实测**。
