## 一、结论先行：7 个视频合起来说了什么

**1. 我们缺的不是检索器，是「读第二条」的通道。**

Headroom 全场最硬的一条不是压缩算法，是 **CCR（compress–cache–retrieve）**的最后一段：压缩后的摘要**附带一个 retrieve 工具**，模型看摘要不够就按需取回原文——压缩从「不可逆的信息丢失」变成「延迟加载」。对照本仓：`src/render.ts:32` 的 `EXCERPT_CHARS = 800` **一刀切**——不论 role、不论 Ω/regime、不论这条是本轮主答案还是边缘邻居，一律取前 800 字；而 `src/tools.ts` 的 13 个 `memo_*` 工具里**没有按 D-id 读全文的入口**，`memo_recall` 的 `query` 是必填参数（`src/tools.ts:928`）。

更精确地说（这是本次核查发现的最强证据）：**全仓唯一接收 `id` 参数的工具是 `memo_update`（`src/tools.ts:1277`），而它是写路径**——改写这篇。也就是说，模型拿到 `D123「标题」…摘要…` 之后，**唯一能按 D 号寻址的动作是「改写它」**。想读全文只能重写一个 query 再赌一次召回。这是「渐进式披露」在本仓最小、也最便宜的落地件。

**2. 顺带查实的一处账实不符（本轮实测，非视频内容）。**

`src/recall.ts:367` 的预算记账是 `estimateTokens(row.body)`——**按全文记**；而 `src/render.ts:41` 实际渲染出去的是 `excerpt()` 截后的 **800 字**。两者对不上。用本桶真语料实测（`~/.dsh/memo-river/b94d8836d6175817/dailynote/dsh-memo-river/` 全量 **246 篇**）：

- 正文 prose 长度 > 800 字的：**229 篇 = 93%**；
- 全量按「全文」记账 est = **191,327**，按「实际渲染」（前 800 字）est = **105,784**，**记账是渲染的 1.81 倍**。

也就是说 **3500 的预算实际只花出约 55%**，剩下 45% 因为「记全文、发 800」而蒸发。Headroom 的 CCR 恰好给了这个差值的正当用途——**先发摘要，把省下的预算留成「按需取全文」的余量**。这条与 §一.1 是同一个改动的两面：**修 excerpt 与记账口径的对齐，同时开 retrieve 通道**，可立刻回收本轮实测的 45% 预算。

**3. 「该给多细」这件事，三份材料从三个方向指向同一个答案：分层 + 按需展开。**

- Agent Skills 版：`SKILL.md`（描述）→ `reference/`（细节）→ `script/`（执行），启动时只加载描述；
- Headroom 版：摘要进上下文，原文留本地 + retrieve 工具；
- CLM 版：干脆把「留什么、何时压缩」从外围 harness **交还给模型自己**（它把对话记录镜像成一个可编辑文件）。

本仓当前是**单层**：候选正文截到 800 字就发出去，没有「展开」选项。三条路都指向同一个缺口。

**4. 「该不该给」我们已经在做，但做的是二元闸门，不是粒度闸门。**

`src/decision.ts` 的判别式门控问的是「读了这条候选记忆之后，会改变当前任务接下来的做法吗？」——这回答的是**给不给**。这 7 个视频里没有任何一家在教「给多细」，只有 CLM 和 Headroom 在演示「给到哪一层」。两者不是一个问题，别把它们合并成一张票。

**5. 有一条反方证据：经验也许根本不该走「检索注入」这条路。**

Trace2Skill（BV1BU5E6pEBL）拿 ReasoningBank 式**检索式经验库**和**蒸馏成静态技能目录**做了同轨迹池对照：human-written + combined 设置下，静态技能在 12B 上 VRF 高 **13.8 个百分点**，35B 上高 **9.2 个百分点**。它给的三个解释直接戳检索路线：① 检索受查询相似度影响，**再分步一次就可能找错片段**；② 检索片段会和任务上下文**抢注意力**；③ 层级合并会去重并抽象成通用原则。

这不能直接推翻记忆河流（它说的是**任务域内的操作规则**，我们存的是**跨任务的历史事实与决策**），但它是我们能拿到的、最像样的一次反向压力测试，**必须记账**。

**6. 一条对我们「拓扑读出是否过度工程」的反问。**

Karpathy 的持久 wiki 在**约 100 篇文章、将近 40 万字**的规模上，明确说「根本不需要什么复杂的 RAG 基础设施，就靠简单的索引文件加上大模型自动维护的摘要就能回答极其复杂的问题」。本仓本桶当前候选约 165 条、语料百级篇数，**规模同级**。

这不是「拆掉 RiverMemo」的论据（两边存的东西不同：他存编译后的摘要，我们存原始日记 + 拓扑），但它是一个需要正面回答的问题：**在百篇量级上，Ω / role / regime 带来的增益，和「好的标题 + 索引 + 正文开头 800 字」相比，谁能赢？** 我建议把这条登记成待验问题，而不是当结论。

### 1. BV1RkFAznESD ｜ Agent Skills 做知识库检索，能比传统 RAG 效果更好吗？

| 项 | 值 |
|---|---|
| UP 主 | code秘密花园 |
| 时长 / 字幕 | 816s ｜ 414 条 ｜ 5379 字 |
| 配套 | github.com/ConardLi/rag-skill/ |

**核心主张**：用 **Agent Skill 的渐进式披露**替代「固定分块 + 向量匹配」的 RAG——不预先建向量库，让 agent 像人一样先缩小目录范围、再精准打开少量文件。作者立场很清楚：他对 chunk+embedding 模式「有比较大的偏见」，认为那是「当下的一种妥协模式」。

**关键机制**

- **渐进式加载三层**：启动时只把 skill 的基础描述塞进上下文 → 命中需求后再读 `SKILL.md` 使用说明 → 再按需读 `reference/`（PDF/Excel 的解析方法）→ 必要时才跑 `script/` 里的脚本（PDF 转图片等）。
- **检索四步**：① 定位领域（读目录索引）→ ② 定位文件（`grep` 类命令筛）→ ③ 按文件类型差异化读关键部分（markdown 定位段；PDF 转纯文本按页/章节取；Excel 只读取相关的表行列）→ ④ 结合上下文拼成**成段可读的回答**，而不是一堆命中行。
- **两条设计原则**：渐进式检索（尽量少读，但读得准）；保持简单可控（用户只说知识库位置，策略由 skill 自己决定）。
- **两个工程技巧**：文件夹按领域划分；**每个文件夹放一个目录索引文件**（字幕「data structure 点 MD」，疑似 `data-structure.md`），多级嵌套时 agent 找到领域后才读该领域的索引。

**实测场景**（作者自建多格式知识库：上市公司财报 PDF / 电商订单 Excel / AI 行业资料 / 安全领域 markdown+TXT）：
三一重工前三大股东（PDF）、航天动力前十大股东、跨两张 Excel 的「郑雪买了啥」（跨表 join：顾客表找人 ID → 订单表查商品）、「哪些用户买了儿童绘本」。

**作者自陈的三条缺陷**（这段最有价值）：

1. **首次检索效率低**——PDF 等特殊格式要先调脚本转换，所以**推荐预处理成纯文本**；
2. **skill 调用稳定性**——多轮检测之后 AI 会忘记调用这个 skill，丢失关键处理步骤（作者说这在很多 skill 上都存在，应从 harness 客户端层面解决）；
3. **token 消耗更大**——整个检索过程由 AI 控制，第一次没找到就换参数继续找，直到命中为止。**结果更准，但 token 可能更多**。

> 第 3 条值得注意：这是「渐进式」的隐性成本——它把 token 从「一次注入」挪到了「多次往返」，总账不一定更便宜。我们做按需展开时必须记住这一条。

**与本仓的可迁移点**

- **需改造（高价值）**：`reference/` 那层对应我们的「按 D-id 取全文」。但我们的第二跳是断的（`memo_recall` 的 `query` 必填，`src/tools.ts` 无 get-by-id）。这是**渐进式披露在本仓落地的最小一件**，与 Headroom 的 `retrieve` 是同一件事的两种说法。
- **需改造（中价值）**：桶层缺「主题分区地图」。`memo_buckets` 给的是桶地图（跨工作区），注入块头部给的是 `+继承=N(桶×n)`；但**本桶内部**有哪些主题分区、各自多少篇，注入块里没有。Agent Skills 的 `data-structure.md` 就是这个位置的产物。
- **可直接用（低成本）**：skill 稳定性那条对我们的直接映射是——**注入块里要把「怎么用」写死**。`src/render.ts:119-137` 的 `methodContract` 已经在做（块尾加一行用法契约），本节给的是这条做法的第二个独立证据源。
- **不适用**：目录索引的人工维护成本。我们的桶是自动索引的（`memo_tags` / `memo_stats`），不需要作者那种「手动写 data-structure.md」。

### 2. BV1AmSSBMErT ｜ 放弃RAG吧！LLM知识库新范式 ｜ Karpathy的新思路

| 项 | 值 |
|---|---|
| UP 主 | 为什么叫QQ |
| 时长 / 字幕 | 436s ｜ 216 条 ｜ 2535 字 |
| 引述 | Karpathy 个人知识库方法、Vannevar Bush 的 Memex（1945） |

**核心主张**：传统 RAG 的根本病不是检索算法不够好，是**知识不积累**——「每次回答你的问题都是在重新发现知识」「即使你的检索准确率达到 100%，大模型依然是在临时拼凑答案」。解法是让 LLM **编译并维护**一个持久化的、互相链接的 markdown wiki。

**关键机制**

- **三层架构（这是全文最有结构的部分）**：
  1. **raw sources 原始数据层**——文章/论文/图片，**不可变**，LLM 只读不写，「真理之源」；
  2. **the wiki 知识库层**——LLM 生成的 markdown（摘要、概念对比、分析），LLM 完全拥有，负责创建页面、维护链接、保持一致性；
  3. **the schema 规则层**——配置文件，告诉 LLM wiki 的结构、遇到新文章该怎么处理。
- **四动作工作流**：`ingest`（摄入 → 读文章、讨论要点、更新相关 wiki 页）→ `query`（向 wiki 提问，搜索相关页合成答案）→ `filing`（**把生成的精彩回答存回 wiki 作为新页面**——作者说这是最重要的一步）→ `lint`（定期体检：找矛盾数据、找没有链接的孤岛页面、甚至联网补缺失信息）。
- **角色重定义**：「obsidian 是 IDE，大模型是程序员，wiki 就是你的代码库」；人从「整理资料的苦力」变成「知识架构师 / 审核员」。

**关键数字（口播）**

- Karpathy 的个人 wiki 已积累**约 100 篇文章、将近 40 万字**；
- 在这个规模下「**根本不需要什么复杂的 RAG 基础设施**，就靠简单的索引文件 + 大模型自动维护的摘要，就能回答极其复杂的问题」；
- 一篇文章可能触及 **10~15 个 wiki 页面**；LLM **一次能处理 15 个文件**；
- 作者引 Karpathy 的话：「每个企业都有一个 ROM 目录，但从来没有人编译过它」（「ROM」疑似误识别）。

**与本仓的可迁移点**

- **可直接用**：**四动作我们已经全有**，而且能一一对上——`ingest` ↔ `memo_write`，`query` ↔ `memo_recall`，`filing`（把回答存回库）↔ `memo_write` 的回合摘要/草稿，`lint` ↔ `memo_patrol`（矛盾/近重复/未命名/枢纽 Tag 四类巡检）。**这是对设计的一次外部确认，不是新增需求。**
- **需改造**：**ingest 时的矛盾检测**。它的「标记出新数据和旧观点的矛盾」发生在**写入那一刻**；我们靠 `memo_supersede` / `memo_write` 的 `supersedes` 参数**手工声明**。写侧目前没有「这条新内容是否与库里已有条目冲突」的自动检测。（注意：跨桶/同桶语义去重已有，那是重复检测，不是矛盾检测。）
- **待验问题（重要）**：见 §一.6。百篇/四十万字量级上「简单索引 + 摘要」的表现，是对我们拓扑读出的直接反问。**建议登记为待验，不要当结论。**
- **不适用**：三层架构里的 schema 层。Karpathy 需要一个可编辑的规则文件是因为 ingestion 是人工触发的；我们的写侧行为已经固化在 `src/prompt.ts:12` 的 `FIXED_CONTRACT_TEXT` 里，不需要用户在桶里维护一份 schema。

### 3. BV1Xg7v6PEDK ｜ 代码搜索省 92% Token？拆解 Headroom 的上下文优化真相

| 项 | 值 |
|---|---|
| UP 主 | 为什么叫QQ |
| 时长 / 字幕 | 813s ｜ 373 条 ｜ 4994 字 |

**核心主张**：Headroom 不是「魔法压缩器」，是**本地上下文优化层**——三阶段管线 + 多个内容专用压缩器，在**官方基准中未观察到明显准确率下降**的前提下拿到高压缩比。真正的洞见不在压缩比，在 **CCR 可逆架构**。

**关键数字（口播）**

- 官方代码搜索基准：token **17,765 → 1,408**，省约 **92%**（标题/简介另称「最高减少 95%」）；
- **输出 token 成本通常是输入 token 的 5 倍**（在「按输出计费」的模型上，这是压缩输入之外的另一条成本杠杆）；
- 对照 Code graph：约省 **57%** token，但**不同仓库波动明显**；
- 运行形态：本地端口 **8787**。

**关键机制**

- **三阶段管线**：`cache aligner`（稳可缓存前缀）→ `content router`（判内容类型，JSON/日志/搜索结果/diff/DF 分别分发）→ **内容专用压缩器**。
- **五个专用压缩器**（各自守一条「不能动什么」的红线）：
  1. **smart crusher（JSON）**：不破坏 JSON 结构，**保留全部键名、结构符号、布尔值与 null**，只压「长篇大论的字符串值」和「冗余的数组元素」——原话比喻：让模型看到「这栋楼有几间房、每间叫什么」，但不必知道「每间房里放了几把椅子」。
  2. **code compressor（AST 感知）**：用 tree-sitter 解析成**抽象语法树**，精准识别 import、函数签名、类型注解、错误处理这些「代码骨架绝对不能动」；再用语义分析给函数打分，**不重要的函数压掉函数体、保留完整签名**。红线：保证语法结构尽量有效、适合概览。
  3. **cache aligner**：把日期、session id 等**易变字段移到尾部**，让前缀字节序列保持稳定，最大化 prompt caching 命中（降 KV cache 的 input 成本）。
  4. **compress（文本兜底）**：在不规则自然语言上训练的通用压缩模型。
  5. **其他**：**log compressor**（合并重复日志行）、**search compressor**（识别真正相关的文件，删掉排名靠后、相关性低的结果）、**diff compressor**（只保留真正改了逻辑的行，过滤纯格式调整）。
- **CCR = compress → cache → retrieve（全文最该抄的一节）**：
  - 一边用上述算法把几万 token 压成几千 token 发给模型，**一边在 TTL 内缓存原文**；
  - 发给模型的同时**附带一个 `headroom retrieve` 工具**；
  - 模型看着摘要能解就省了 token；**觉得摘要不够就主动调 retrieve 向本地代理请求原始数据**；
  - 原文结论：「压缩不再是不可逆的信息丢失，而变成了一种**延迟加载（lazy loading）**的策略。他把决定权交给了大模型自己。」
- **底层成本模型**：引前谷歌 TPU 架构师 Reiner Pope 的七方程与 **Roofline 模型**——推理常受**内存带宽**而非算力限制；**KV cache** 随上下文线性膨胀，吃显存、限并发 batch size。所以省 token 不只是省钱，是打破物理瓶颈。
- **工程哲学**：「先给骨架再给细节，先给索引再给内容」；Code graph 是**主动检索**（需要时精准找那几行），Headroom 是**被动展开**（先给全局概览，不够再要全文），两者互补成一套渐进式上下文方案。
- **其他功能**：`verbosity steering`（在系统提示里加一句「给我简短点、别复述上下文」）；`headroom learn`（从失败回合沉淀规则，并找出哪里压缩过度）；三种用法（代理包装一行命令 / 本地代理 / 库模式）。

### 6. BV1BU5E6pEBL ｜ 阿里 Qwen 新论文 Trace2Skill

| 项 | 值 |
|---|---|
| UP 主 | Agent智能体深度研究院 |
| 时长 / 字幕 | 740s ｜ 297 条 ｜ 3941 字 |
| 论文 | Trace2Skill: Distill Trajectory-Local Lessons into Transferable Agent Skills，arXiv **2603.25158** |
| 作者单位 | 阿里巴巴 Qwen 大模型应用团队 + 苏黎世联邦理工 + 苏黎世大学 + 北京大学 + 浙江大学 |
| 版本 | 字幕「二零026年4月27日的 RXIV14，标注 work in progress」→ 疑为 2026-04-27 的 arXiv v1 |

**核心主张**：agent 跑过的成功和失败记录，**不一定要变成检索记忆，也不一定要拿来训练模型**，而可以被**压缩成一份可迁移的操作手册（skill）**。核心判断是——单条轨迹确实局部，但**大量轨迹里反复出现的错误修复方式和成功动作，往往反映任务域里的稳定规律**。

**方法（三步）**

1. **轨迹生成**：固定参数的 ReAct agent 带初始技能跑任务，收集成功轨迹 + 失败轨迹。
2. **并行多 agent 补丁提案**：每个分析 agent **只看一条轨迹**，产出 **skill patch**（对技能说明书的编辑建议：插入注意事项 / 删除误导性规则 / 更新某步骤）。
   - **成功分析**（单轮）：清理并找关键成功行为；
   - **失败分析**（多轮 ReAct）：读完整日志、输入输出文件、标准答案，**反复定位根因并用最小修复验证**；找不到可复现原因、或修复不能解释失败 → **该轨迹不进补丁池**。
3. **无冲突层级合并**：每层把一组补丁交给同一个 LLM 归纳、去重、解冲突，保留**独立轨迹里反复出现的模式**，转成类 diff 编辑操作并做**程序检查**（引用不存在文件的补丁拒绝、同文件同范围冲突编辑暂缓），更新后的目录还要过格式校验。

**为什么反对顺序更新**（这条对我们写侧很关键）：边跑边改会让后面的分析看到**已经被前面轨迹改过的技能**，容易出现**顺序漂移**——早期偶然错误被写进技能，后续再围绕这个版本继续修补。类比：「让一组审稿人同时看不同案例，最后再统一归纳」。

**两种模式**：`deepening`（从人类专家写的技能出发继续加深修补）/ `creation`（先让模型凭参数知识写草稿，再用轨迹证据把它变成有用技能）。论文强调**参数草稿本身接近无技能**，真正起作用的是轨迹驱动的演化。

**关键数字（口播）**

- 实验域：`SpreadsheetBench Verified` 400 样本 → 200 演化 / 200 测试；soft / hard 迁移，另用 **WikiTableQuestions** 转成表格形式；
- 模型：Qwen **3.5 12B / 10B / 35B** 系（字幕「困3.5122BA10B和35BA3B」，存疑）；
- **12B 写出的 deepening+combined，让 12B 用户在 SpreadsheetBench Verified 上相对「人工技能」提升 21.50 个百分点**；
- **35B authored creation+error，给 12B 用户在 WikiTableQuestions 上相对 parametric 提升 57.65 个百分点，绝对 81.38%，超过 human-written 的 74.68%**（⚠️ 这是很具体的设置，**不能理解成所有任务平均都提升这么多**）；
- **补丁主题分布**（323 个 merged patches，论文口径最扎实的一处）：公式重算与写回验证 **178 次**、`openpyxl` 优先于 `pandas.to_excel` 的工具选择 **177 次**、显示读回验证 **138 次**、结构编辑安全 **53 次**；

**「静态技能为什么反而比检索记忆强」——论文给的三个解释**（本文最有迁移价值的部分）

1. **检索受查询相似度影响**，分步一遍就可能找错检索片段；
2. **检索片段会和任务上下文抢注意力**；
3. **层级合并会去重并抽象成通用原则**。

**论文自陈的两条限制**（同样是很好的对照物）

1. 目前是**整体合并补丁**，难以量化单个 patch 的边际因果贡献，也难看出补丁之间是否互相干扰；
2. **推理时还没有追踪 agent 具体用了技能目录的哪些 section** —— 后续需要细粒度归因和自动减脂。

### 7. BV1z49NBmEtj ｜ Codebase Memory：让大模型 1 秒看懂整个项目

| 项 | 值 |
|---|---|
| UP 主 | 沐冰茶 |
| 时长 / 字幕 | 534s ｜ 193 条 ｜ 2534 字 |

**核心主张**：AI 编程助手慢且贵的根因是**表征错配**——「在大语言模型眼里，你的整个代码库就是一堵扁平的、长长的文本墙」，而代码实际是「函数调用 / 依赖关系 / 模块化结构」组成的立体网络。解法：**别让 AI 逐字读代码，直接给它一张预先建好的地图**（知识图谱）。

**关键机制**

- **三步架构**：① **解析**（tree-sitter，从语法层面理解）→ ② **构建**（流水线拼成完整知识图谱）→ ③ **服务**（把查询能力打包成 **14 个工具**，通过**标准协议**交给 AI agent）。
- **覆盖面**：**66 种编程语言**。
- **部署极简**：整个系统是**一个二进制文件 + 一个 SQLite 文件**，无外部依赖、无需维护复杂数据库。

**关键数字（口播，与文件浏览器硬碰硬对照）**

| 指标 | Codebase Memory | 传统文件浏览 | 差距 |
|---|---|---|---|
| 答案质量（准确率） | **83%** | **92%** | 接近 |
| 工具调用次数 | — | — | **少一半多（2.1 倍）** |
| token 消耗 | **1,000** | **10,000** | **少 10 倍** |
| 查询延迟 | **< 1 ms** | **几十秒** | **快 100 倍以上** |

**最重要的判断（论文自己的结论）**：**「未来的最佳架构是一种混合模式」**——不是用地图取代读代码，而是分工：**搞清楚整体结构、谁调用了谁这类宏观问题 → 查地图（快准狠）；要看某一行代码具体怎么写 → 回原文件**。

**vs RAG**：RAG 是「大海捞针一样捞相关文本片段」；Codebase Memory 的优势是**真正的结构化查询**——「懂代码的逻辑，而不仅仅是文本长得像不像」，且用 SQLite 而非笨重的向量数据库，还能**自动跟代码保持同步**。

**工程侧**：八层自动化安全审计（每次代码提交都跑：静态分析、扫密钥、监控网络、防数据泄露、防 SQL 注入等），发布前用 **70+ 种杀毒引擎**扫一遍。

**与本仓的可迁移点**

- **可直接用（架构确认）**：**混合模式 = 我们已经是的形态**。`src/recall.ts` 的读出链是「拓扑（Ω/role/regime，结构）+ 正文片段（`chunk.content`，细节）」——正好对上「宏观查图谱、细节回原文件」。**这是外部论文对我们架构选择的一次确认**，可以写进 DESIGN 的背景引证。
- **需改造（识别真实差距）**：它的「结构」是**可查询的图**（14 个工具、按符号/调用关系精确查）；我们的「结构」是**两个标量**（`omega`、`role`）+ 召回时的一次 Tag 共现扩展。**差别不在有没有结构，在结构能不能被查询。** 具体缺口：Tag 共现图目前**只在召回时内部扩展**，没有暴露成「这个 Tag 下有哪些篇 / 这两篇通过哪些 Tag 相连」的接口（`memo_tags` 只给频次，没有关系）。
- **需改造（数字读法，很重要）**：**83% vs 92% 是答案质量更低**。它赢在效率（token 少 10 倍、延迟快 100 倍），不是赢在准。**这提醒我们：结构化/拓扑路线天然有「省成本、损精度」的取向。**
  → 对本仓的直接意义：`src/config.ts:341` 的 `minKnnForReward = 0.6` 与 `src/recall.ts:625` 的 `rewardSuppressed` 逻辑，本质是**承认低 KNN 候选不发奖励分**。这条视频给了这个设计一个外部注脚：**结构加成不能替代 KNN 基线，只能在不损精度的前提下换效率。**
- **不适用**：tree-sitter 解析（我们不是代码库）、八层安全审计（半径与场景都不同）。
